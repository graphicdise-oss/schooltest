# Capacitor ง่ายกว่าจริงไหม — วิเคราะห์ละเอียด

เอกสารนี้ตอบคำถาม "ถ้าใช้ Capacitor จะง่ายกว่า Flutter/React Native หรือเปล่า"

**คำตอบสั้น: ง่ายกว่าจริง แต่ง่ายกว่า "น้อยกว่าที่คิด" มาก
และจะง่ายกว่าเฉพาะบางรูปแบบการใช้งานเท่านั้น**

---

## 1. เรื่องที่คนมักเข้าใจผิด: Capacitor มี 2 โหมด ไม่ใช่โหมดเดียว

ความเข้าใจทั่วไปคือ "Capacitor = เอาเว็บ Laravel มาห่อเป็นแอป จบ"
ความจริงมี 2 วิธี และต่างกันคนละเรื่องเลย

### โหมด A — Remote URL (ชี้ไปที่เว็บจริง)
```ts
// capacitor.config.ts
server: { url: 'https://school.example.com/parent', cleartext: false }
```
แอปคือเบราว์เซอร์ที่เปิดเว็บคุณอยู่ตลอด

* ✅ **ไม่ต้องทำ API เลย** ใช้ Blade + session เดิมได้ทั้งหมด
* ✅ เขียนโค้ดแอปแค่ไม่กี่สิบบรรทัด
* ✅ แก้เว็บ = แอปเปลี่ยนตามทันที ไม่ต้องส่ง Store ใหม่
* ❌ **ไม่มีเน็ต = จอขาว** ใช้ไม่ได้เลย
* ❌ **เสี่ยงโดน Apple ปฏิเสธสูงมาก** (Guideline 4.2 Minimum Functionality)
* ⚠️ Google Play ผ่อนปรนกว่ามาก แต่ก็มีนโยบาย Minimum Functionality เหมือนกัน

### โหมด B — Bundled assets (ฝัง HTML/JS ไว้ในแอป แล้วยิง API)
แอปมีไฟล์เว็บอยู่ในตัว เรียกข้อมูลจาก Laravel ผ่าน REST API

* ✅ ออฟไลน์ได้จริง เปิดแอปแล้วเห็นข้อมูลทันที
* ✅ ผ่านรีวิว App Store ได้
* ❌ **ต้องทำ API (เฟส 0) เหมือนทาง Flutter ทุกประการ**
* ❌ **ต้องเขียน frontend ใหม่** (SPA) — ใช้ Blade ไม่ได้แล้ว เพราะ Blade เรนเดอร์ที่เซิร์ฟเวอร์
* ❌ ต้องเปลี่ยนจาก session cookie ไปเป็น token auth

### ตารางเทียบตรง ๆ

| | Capacitor โหมด A | Capacitor โหมด B | Flutter / RN |
|---|---|---|---|
| ต้องทำ API Laravel | ❌ ไม่ต้อง | ✅ ต้อง | ✅ ต้อง |
| ต้องแยก Service / ThaiDate / API Resource | ❌ | ✅ | ✅ |
| ต้องเขียน UI ใหม่ | ❌ ใช้ Blade เดิม | ✅ HTML/JS | ✅ Dart / TSX |
| ออฟไลน์ | ❌ | ✅ | ✅ |
| Push Notification | ✅ | ✅ | ✅ |
| ผ่าน Play Store | ⚠️ น่าจะผ่าน | ✅ | ✅ |
| ผ่าน App Store | ❌ เสี่ยงสูง | ✅ | ✅ |
| แรงที่ใช้ | **~2 สัปดาห์** | **~6–7 สัปดาห์** | ~7–9 สัปดาห์ |

### ข้อสรุปที่สำคัญที่สุด

> **โหมด B ใช้แรงพอ ๆ กับ Flutter** เพราะงานหนักจริง ๆ อยู่ที่ฝั่ง Laravel
> (เปิด API, แยก Service, รวมศูนย์ พ.ศ., ทำ API Resource) ซึ่งเหมือนกันเป๊ะ
> ส่วนที่ต่างกันเหลือแค่ "เขียน UI ด้วย HTML/JS หรือ Dart"
>
> **ถ้าทีมมีพื้นฐาน Flutter/RN อยู่แล้ว ข้อได้เปรียบของ Capacitor แทบหายไปหมด**

Capacitor จะ "ง่ายกว่าอย่างชัดเจน" ก็ต่อเมื่อยอมรับโหมด A ได้เท่านั้น

## 2. ปัญหาที่จะเจอแน่ ๆ จากโค้ดปัจจุบัน (ทั้งสองโหมด)

ตรวจจากโค้ดจริงในโปรเจกต์นี้:

### 2.1 ปุ่มพิมพ์ตารางเรียนจะพัง
`resources/views/parent/timetable.blade.php:9`
```html
<a href="{{ route('parent.timetable.print') }}" target="_blank">
```
`resources/views/parent/timetable_print.blade.php:48`
```html
<button onclick="window.print()">🖨️ พิมพ์ตารางเรียน</button>
```

ใน webview:
* `target="_blank"` — ไม่เปิดอะไรเลย หรือเด้งออกเบราว์เซอร์ข้างนอก (หลุด session)
* `window.print()` — **WKWebView (iOS) และ Android WebView ไม่รองรับ**
  กดแล้วเงียบ ไม่มีอะไรเกิดขึ้น

**ต้องแก้:** ทำ endpoint ฝั่ง Laravel คืนไฟล์ PDF แล้วให้แอปเปิดด้วย
`@capacitor/browser` หรือส่งเข้า share sheet ของเครื่อง
(งานนี้ต้องทำเหมือนกันหมดไม่ว่าเลือกทางไหน)

### 2.2 ไฟล์แนบประกาศแสดงได้เฉพาะรูป
`resources/views/parent/announcement_show.blade.php:12`
```blade
@if($announcement->attachment_path)
<img src="{{ asset('storage/' . $announcement->attachment_path) }}" ...>
```
ตอนนี้ยัดทุกไฟล์ลง `<img>` — ถ้าครูแนบ PDF/Word ผู้ปกครองจะเห็นรูปแตก
(เป็นบั๊กที่มีอยู่แล้วบนเว็บ ไม่เกี่ยวกับแอป แต่จะเห็นชัดขึ้นมากบนมือถือ)

**ต้องแก้:** เช็คนามสกุลไฟล์ ถ้าไม่ใช่รูปให้แสดงเป็นการ์ดดาวน์โหลด

### 2.3 CSS/JS โหลดจาก CDN ทั้งหมด
`resources/views/parent/layout.blade.php` โหลด Bootstrap, Bootstrap Icons,
Google Fonts จาก CDN → **แคชออฟไลน์ไม่ได้** และเน็ตช้าจะเห็นหน้าเปล่าก่อน
ต้องย้ายมาไว้ในโปรเจกต์ (งานนี้ก็ต้องทำทุกทางเลือกเหมือนกัน)

### 2.4 เมนู 7 อันแนวนอน ใช้บนมือถือไม่สะดวก
`pp-nav` มีลิงก์ 7 อัน `flex-wrap` — บนจอมือถือจะตกบรรทัดเป็น 3 แถว
ควรเปลี่ยนเป็น bottom tab bar 4–5 อัน + ที่เหลือยุบใต้ "เพิ่มเติม"

### 2.5 (เฉพาะโหมด B) session cookie จะใช้ไม่ได้
`config/session.php` ตั้ง `same_site = 'lax'`

ในโหมด B webview รันที่ origin `capacitor://localhost` (iOS) /
`http://localhost` (Android) → การเรียก `https://school.example.com/api`
กลายเป็น **cross-site** → cookie แบบ `SameSite=Lax` **จะไม่ถูกส่งไปเลย**

ทางแก้มี 2 ทาง:
* ตั้ง `SESSION_SAME_SITE=none` + `SESSION_SECURE_COOKIE=true` + เปิด CORS
  → ทำได้ แต่ลดระดับการป้องกัน CSRF ของ **ทั้งระบบ** รวมหลังบ้านด้วย ไม่แนะนำ
* **เปลี่ยนไปใช้ Sanctum token** → คือกลับไปทำเฟส 0 อยู่ดี ✅ แนะนำทางนี้

## 3. แล้วสรุปควรทำอะไร

เมื่อรู้แล้วว่าโหมด B ไม่ได้ประหยัดกว่า Flutter จริง
แผนที่คุ้มที่สุดสำหรับโรงเรียนคือ **แบ่งตาม platform** ไม่ใช่เลือกเทคโนโลยีเดียวรวด

### ขั้นที่ 1 — PWA (1–2 สัปดาห์) ทำก่อนเลย
ทำครั้งเดียว ได้ประโยชน์กับทุกแผนถัดไป และเป็นฐานของ Capacitor โหมด B ด้วย
* ย้าย CDN มาไว้ในเครื่อง
* ปรับ layout เป็น mobile-first + bottom nav
* เพิ่ม `manifest.json` + Service Worker
* แก้ปุ่มพิมพ์ + ไฟล์แนบตามข้อ 2.1 / 2.2

ผู้ปกครองกด "เพิ่มลงหน้าจอโฮม" ใช้ได้ทันทีทั้ง Android และ iOS ไม่เสียค่า Store

### ขั้นที่ 2 — Capacitor โหมด A ขึ้น Play Store เท่านั้น (+1–2 สัปดาห์)
* ได้ไอคอนแอปใน Play Store ตามที่ลูกค้าอยากได้ ด้วยแรงน้อยมาก
* ผู้ปกครองโรงเรียนรัฐส่วนใหญ่ใช้ Android → ครอบคลุมคนส่วนใหญ่แล้ว
* ใส่ Push Notification (FCM) ผูกกับตาราง `announcements` ที่มีอยู่แล้ว
  → มีฟีเจอร์ native จริง ไม่ใช่เว็บครอบเปล่า ๆ
* ค่าใช้จ่าย 25 USD ครั้งเดียว

**อย่าส่งโหมด A เข้า App Store** — โอกาสโดนปฏิเสธสูงมาก และเสียเวลารีวิวหลายรอบ

### ขั้นที่ 3 — iOS ค่อยตัดสินใจทีหลัง
พอถึงจุดนี้จะมีข้อมูลจริงแล้วว่าผู้ปกครองใช้ iOS กี่เปอร์เซ็นต์
* ถ้าน้อย → ปล่อยให้ใช้ PWA บน iOS ต่อไป (Safari รองรับ Add to Home Screen + Push ตั้งแต่ iOS 16.4)
* ถ้าเยอะจนต้องขึ้น App Store → **ตอนนั้นเลือก Flutter/RN ไปเลย**
  เพราะต้องทำ API อยู่ดี และทีมมีพื้นฐานอยู่แล้ว
  ไม่มีเหตุผลจะไปทำ Capacitor โหมด B ให้ได้ของที่ด้อยกว่าในราคาเท่ากัน

## 5. งานที่ต้องทำเหมือนกันหมดทุกทางเลือก

ไม่ว่าจะเลือกทางไหน 5 ข้อนี้ต้องทำ ทำก่อนได้เลยไม่เสียเปล่า:

- [ ] ย้าย Bootstrap / Icons / Fonts จาก CDN มาไว้ในโปรเจกต์
- [ ] ปรับ `parent/layout.blade.php` เป็น mobile-first + bottom nav
- [ ] แก้ปุ่มพิมพ์ตารางเรียน → ให้เซิร์ฟเวอร์คืน PDF แทน `window.print()`
- [ ] แก้ไฟล์แนบประกาศให้รองรับไฟล์ที่ไม่ใช่รูป
- [ ] สร้าง `App\Support\ThaiDate` รวมศูนย์ พ.ศ. (ดู `MOBILE_APP_NATIVE.md` ข้อ 3)

ทั้ง 5 ข้อเป็นการปรับปรุงเว็บที่ดีขึ้นในตัวเองอยู่แล้ว
แม้สุดท้ายจะยังไม่ทำแอปก็ไม่เสียของ
